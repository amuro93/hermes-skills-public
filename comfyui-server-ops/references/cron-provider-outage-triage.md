# 「全部 cron 一起掛」的分層鑑識通則

症狀：一早起來，`hermes cron list` 裡所有 job 的 `Last run` 都是同一種錯誤
（例如 `RuntimeError: ... streaming request failed: [WinError 10060] 連線嘗試失敗`）。
看起來像「排程壞了」，實際上通常是**好幾層同時出問題**。以下是不帶帳號資訊的通則版。

## 一、先別急著修 job，先把「失敗」分類

同一批失敗的 job，逐一問三件事：

1. **腳本本身跑了嗎？**（pre-run script 可能已經執行完，只有「回報」沒送出）
2. **產物產生了嗎？**（圖／檔可能已經落在磁碟上，只是交付失敗）
3. **是產線失敗，還是只交付失敗？**

實務經驗：一次全掛的事件裡，常見的是「3 個 job 的產物都在，只有通知沒送出」。
⇒ **看到失敗通知先去看產物存不存在**，比重新跑一輪便宜太多。

## 二、逐層證據（由外往內）

| 層 | 看什麼 | 典型訊號 |
|:--|:--|:--|
| ① 出口網路 | 多個**不同供應商**的 API 同時 timeout／`getaddrinfo failed` | 三家同時失敗 ⇒ 不是 provider 的鍋 |
| ② DNS | `getaddrinfo failed`、DNS 設定只有單一內網伺服器 | 只有一條 DNS ⇒ 掛掉就全掛 |
| ③ 區網／本機服務 | 本機服務的 `GET /system_stats` 是否仍 200 | 區網正常＋對外全掛 ⇒ WAN／DNS 問題 |
| ④ 機器層 | gateway 的 `previous_unclean_exit`、Windows 事件 1074（重開機）、DHCP／WLAN 服務停啟時間 | 時間對得上 ⇒ 是重開機／斷網，不是程式 |
| ⑤ 恢復驗證 | 對外端點回 `401`／`403`（連得到但沒帶 key） | 回 401/403 ＝ 網路已恢復，不是還在斷 |

- 🔴 **「Telegram 還活著」不能當對外網路正常的證據**：它可能走 sticky IP、不經 DNS 解析。
- 🔴 **同一個 fallback 鏈裡，兩段指向同一個 backend 會被跳過**（`Fallback skip: ... resolves to the same backend`）—— 這種訊息最容易被誤讀成「fallback 壞了」。

## 三、處置原則

1. **先對帳再重跑**：pre-run 已執行的不要重跑；產物已落盤的直接補送。
2. 只有真的沒產出的那支才重跑，而且用背景執行＋log，不要綁在會斷的 session 上。
3. 交付前逐檔驗證（`exists()` ＋ size），**不要只信 JSON／stdout 裡的字串**。

## 四、設計面：長產線不要跟「回報」綁在同一個 session

（上面是事後鑑識；這節是**事前就該遵守**的規則）

- **症狀形狀**：agent session 的 provider 斷線／被判定無回應 → session 中斷（`cron_incomplete_no_output`）→
  **它啟動的 subprocess 一起被帶走** → 長腳本沒跑完。使用者收到的是一封「失敗通知」，
  但其實 GPU 端早就出一堆成品了 —— **靜默失敗比報錯危險**。
- **兩條防線（缺一不可）**：
  1. **產物先落盤**：長腳本每完成一項就寫進度 JSON（`*_partial.json`）
     → 程序被砍也看得出「哪幾支好了、哪幾支要補」。
  2. **成品要在產線端可尋回**：ComfyUI 的成品留在 `output/` 與 `/history`，
     用 `prompt_id`／檔名前綴就能 `GET /view` 補抓 → **不必重跑、不必再花錢**。
- **交付與產線分離**：交付改成「另一個短命 session（只讀磁碟＋送訊息）」或腳本自己收尾，
  這樣 provider 斷線只損失通知、不損失產物。

## 五、可預防的兩個設定（動網路／設定前先問機器主人）

- **DNS 只有一台** ⇒ 加公共 DNS（1.1.1.1／8.8.8.8）當備援。
- **fallback 鏈只有雲端一段** ⇒ 可加一台地端模型當最後保險，
  這樣 WAN／DNS 掛掉時 cron 至少還能把「產物已經出好」的報告送出來。
